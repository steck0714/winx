# R368 — 音量ボタンを Windows のボタン配列（PNP0C40）として DSDT に追加する（R367 ベース）

## 変更点

### 1. `Dsdt-R368.asl`：`Device (BTNS)` を追加（R367 の GPI0 はそのまま）

| 項目 | 内容 |
|---|---|
| `_HID` | `"PNP0C40"`（Windows 標準のボタン配列。Windows に元から入っている HID のボタンのドライバーが使う） |
| GpioInt 0 | `\_SB.GPI0` のピン **190（PX6、音量＋）**。Edge、ActiveBoth、PullUp、デバウンス 0 |
| GpioInt 1 | `\_SB.GPI0` のピン **191（PX7、音量−）**。同上 |
| `_DSD` | ボタン配列用の UUID `fa6bd625-...`。どの GpioInt がどのボタンかを、HID の使用法で指定する（Portable Device Control のコレクション、0 → Volume Increment 0x0C/0xE9、1 → Volume Decrement 0x0C/0xEA） |

- ピンの番号と、アクティブ Low であることは、L4T の `gpio-keys` から。
- **電源ボタンは、まだ入れていない。** PMIC の MAX77620 経由が本命で、PX5 につながっているかは未確認。何もつながっていないピンを電源ボタンにすると、勝手にスリープする危険がある。

### 2. UEFI：ボタンの状態を表示する

`USB STATUS #1〜#4` のたびに、次の1行を追加で表示する。

`R368 buttons: PX5(power?)=. PX6(vol+)=. PX7(vol-)=. (0 = pressed) CNF=.. OE=..`

この表示が出ている間に電源ボタン（短く）や音量ボタンを押すと、どのピンが反応するかを確かめられる。

- SHA-256: `0a9adef9dbf400c0dff73bbbbbb0e7b555b10b21006040b62fb228d4f310c8ae`
- ビルド: 完了。`EDK_SOURCE_RESTORE_MATCH=YES`。
  - iasl の警告は 3128 の1件だけ。これは元の DSDT の `GCRS` に由来するもので、R367 でも出ていた。

- **未確認:** 実機での動作。

## 試験の手順

1. **UEFI で確かめる。** R368 で起動し、`R368 buttons` の行が出る間（起動して数十秒後、5秒ごとに4回）に、次を順に試して撮影する。
   - 音量＋を押したままにする → `PX6=0` になるか
   - 音量−を押したままにする → `PX7=0` になるか
   - 電源ボタンを**短く**押す（長押しは電源が切れるのでしない） → `PX5` が変わるか
2. **Windows で確かめる**（段階1の GPIO ドライバー v2 がインストール済みであること）。
   - デバイスマネージャーで、`ACPI\PNP0C40`（「HID Button over Interrupt Driver」など）が正常に動作しているか
   - 音量ボタンを押して、画面に音量の表示（OSD）が出るか
3. **結果を共有する。** 段階1のスクリプトで状態も見られる（`Stage1-Gpio.ps1 -Mode Status`）。

## UEFI での結果（2026-10-25、ユーザー報告）

- **音量ボタン:** 押すと `PX6`・`PX7` が **1** になる（離しているときは 0）。
  - L4T（`GPIO_ACTIVE_LOW`）、UEFI の `SidebandButtons.c`（`!gpio_read` で押下と判断）、Hekate はどれも「押すと 0」としているので、**逆になっている**。
  - 原因は未確認。pinmux のプルの設定や、この画面の読み方の違いが考えられる。
  - Windows では ActiveBoth（両方のエッジ）なので割り込みは来るはず。ただし、押した・離したが逆に扱われる可能性がある。
- **電源ボタン:** 短く押しても `PX5` は**変わらない**。電源ボタンは GPIO（PX5）にはつながっておらず、PMIC の MAX77620 の ONOFF 経由で読む必要がある（段階4、I2C5 が必要）。

## もし起動しなくなったら

R367 の ROM で起動すれば、BTNS が無い状態に戻る。
