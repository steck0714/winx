# Native Vulkan on Switch Lite

## Goal and scope

Run Vulkan workloads on the Maxwell GM20B GPU in a Nintendo Switch Lite (HDH-001, T214) under Windows 11 ARM64. Use mesa-switch's NVK core and a native Windows kernel backend. The current Windows desktop uses CPU software rendering.

First prove GPU execution and readback, then off-screen Vulkan drawing, then stable window presentation. Evaluate Direct3D-to-Vulkan integration for desktop composition separately. Game compatibility is outside this project. Keep the bootable landscape desktop, existing Windows installation and all SD partitions throughout bring-up. The default experimental GPU profile is **729.6 MHz**, with **1228.8 MHz** as an optional profile in the existing `LitePerformanceCheck` tool. Both use T214 C1 NA PLL control; hardware frequency and execution must be measured before reporting them active.

Continue implementation, compilation and necessary host checks autonomously until the next step requires a physical Lite test. A progress report, successful build or source push is not a stopping point. Consolidate source corrections and local validation before an owner hardware handoff; do not request a card swap/test for each incremental probe change. After each implementation batch passes its necessary checks, push its source to both repositories' `vulkan-test` branches and update the firmware's driver-submodule pin. The default documentation links here and `sc7-test` stays unchanged.

## Current stage and evidence

The first milestone is a GPU-written word read back by Windows. Probe **0.1.0.8** failed four consecutive default-profile runs at **Stage 304 / E6**. Both fence words stayed `DEADBEEF`; USERD GET/PUT stayed **0/1**, the scheduler was enabled with no reported error, the runlist length was one, and CCSR remained `11000001` (pending). PBDMA reported no valid channel zero. Its changing GP base/fetch/GET/PUT values are therefore **invalid context observations**, not execution progress; the earlier 0.1.0.7 GP-base comparison cannot establish a loaded RAMFC mismatch. Clock measurement remained **729.6 MHz** at 800 mV, BOOT0 `12E000B1`, power/clock/restore `0`, ownership `0`. Earlier short checks measured 1227.8 MHz at 925 mV for the optional profile; neither profile has an execution or stability pass. Local candidate **0.1.0.10** combines saved-context bootstrap with a reconciled cold frontend: persistent idle-slowdown suppression, FIFO clock/timeout setup, LTC/FB routing and two FB flushes before submission. It also suppresses invalid PBDMA counters and captures BUS/PRI failures. It is **not installed**; the owner is not being asked to repeat the previous test.

## Implementation decisions

1. **Kernel backend.** Use Microsoft's render-only sample for WDDM device, context, paging, submission, interrupt and timeout-recovery callbacks. Implement T214 rail, clock, reset, firmware, FIFO and engine bring-up using Linux nouveau as the hardware reference. Use deko3d to check Maxwell packet ordering and fences. Start with an opt-in render adapter alongside the existing display. [Microsoft WDDM sample](https://github.com/microsoft/graphics-driver-samples/tree/de4a2161991eda254013da6c18226f5ea06e4a9c/render-only-sample/roskmd) · [nouveau Tegra platform](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/nouveau/nvkm/engine/device/tegra.c) · [GM20B graphics engine](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/nouveau/nvkm/engine/gr/gm20b.c) · [deko3d queue](https://github.com/devkitPro/deko3d/blob/373bfd43d8b2d805fa2eb7d406dbb823032df958/source/dk_queue.cpp)
2. **Memory and synchronization.** Back GPU allocations with VidMm-managed system memory. GM20B tables are 128 KiB; WDDM system-segment tables are limited to 4 KiB, so the page-table pool must use a dedicated nonzero CPU-visible segment. The CPU-update helper handles aligned byte addresses, validates the complete update before publishing, and rejects unsupported attributes. TLB timeout/read errors remain failures; the caller must keep pages pinned until completion. The segment backing now uses bounded WDDM 2.4 contiguous allocation, a CPU-visible descriptor marked `PopulatedFromSystemMemory`, whole-span offset resolution and retryable cleanup. Root sizing rounds to CPU pages, RAMIN enforces the reported entry limit, and failed root moves make the context unschedulable until a valid binding exists. VidMm owns allocation inside it. Native WinPE tests use real WDK structures with controlled OS-call substitutes; real Dxgkrnl allocation, mapping aliases and DDI integration remain open. Microsoft restricts `CPU_VIRTUAL` updates for local memory segments; the current CPU helper must not be advertised as a complete adapter paging mode. The new paging-buffer backend implements deferred GPU-physical records and the mandatory initial CPU update path; actual adapter dispatch and hardware queue binding still need integration; context references and synchronized fence notification now have tested backend implementations. [WDDM table segments](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_page_table_level_desc) Establish the relationship between Windows allocations, GPU virtual addresses and Tegra IOMMU mappings. Track residency, CPU/GPU cache visibility, channel ownership and fence completion before recycling pages. Report completion and faults to the Windows scheduler. [WDDM GPU virtual memory](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-memory-in-wddm-2-0)
3. **ARM64 Vulkan ICD.** Keep NVK's Maxwell compiler and command generation. Implement Windows device discovery, allocation, mapping, submit and wait behind the NVK `nvkmd` interface. The Switch backend delegates those operations to Horizon services and ships a static library. Build an ARM64 Windows ICD DLL, register its JSON manifest and match its physical device to the WDDM adapter LUID. [NVK backend interface](https://github.com/danfromtico/mesa-switch/blob/0ff52079ca9e9e837ed27eb95a8d239f439a1864/src/nouveau/vulkan/nvkmd/nvkmd.h) · [Switch adapter](https://github.com/danfromtico/mesa-switch/tree/0ff52079ca9e9e837ed27eb95a8d239f439a1864/src/nouveau/vulkan/nvkmd/switch) · [Khronos loader interface](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md)
4. **Window presentation.** Implement `VK_KHR_win32_surface` and `VK_KHR_swapchain` using a presentation allocation and fence the Windows display path can consume. Mesa's current Win32 DXGI route expects a D3D12 command queue. Its other route copies through a CPU mapping and GDI. A GPU-backed presentation route must be demonstrated explicitly. [Mesa Win32 WSI](https://github.com/danfromtico/mesa-switch/blob/0ff52079ca9e9e837ed27eb95a8d239f439a1864/src/vulkan/wsi/wsi_common_win32.cpp) · [Vulkan WSI](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html)
5. **Desktop composition.** After Vulkan presentation works, evaluate a Windows Direct3D user-mode driver or translation layer backed by NVK that DXGI and DWM can actually select. Verify shared surfaces, formats and fence interoperability. Compare the same desktop workload against the software baseline using compositor frame times, CPU usage and GPU activity attributed to `dwm.exe`. [Windows composition and shared resources](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/rendering-on-a-discrete-gpu-using-cross-adapter-resources)

## Hardware acceptance in order

| Step | Evidence required from Windows on HDH-001 |
| --- | --- |
| 1. Execute and read back | Initialize a sentinel in an isolated allocation. Submit a GM20B report with a different value, observe its hardware fence, invalidate the CPU mapping as required and read the expected word. Repeat with a new value. |
| 2. Draw with Vulkan | Load the ARM64 ICD, identify the GM20B adapter and draw a known triangle off-screen. Compare GPU-produced pixels against expected foreground and background samples. |
| 3. Present reliably | Present a changing frame sequence in a landscape HWND. Record the adapter, transport, frame count and duration. Exercise resize and swapchain recreation and check for stale frames, device loss and GPU timeouts. |
| 4. Assess DWM separately | Show hardware work from the compositor and compare frame pacing with the baseline. An application drawing or presenting a triangle satisfies only the corresponding Vulkan step. |
