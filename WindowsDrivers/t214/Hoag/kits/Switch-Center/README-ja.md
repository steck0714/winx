## v0.5.2（2026-10-27）: 新しいドライバーも OTA で入れられるように

- **調べるデバイスを manifest から作る。**
  - アプリが知っている8つのデバイスに加えて、manifest に載っているデバイス（ハードウェア ID）も全部見る。
  - アプリが知らないものは、manifest の名前（`nameJa`、`nameEn`）で表示する。名前が無いときはサービス名で表示する。
  - これで、新しいデバイス（例: 音の SWOA0901）のドライバーを、コントロールセンターを直さずに配れる。
- **UEFI の判断を変えた。**
  - デバイスが DSDT にあれば、UEFI は足りていると見なす。
  - `minUefi` は、デバイスが無いときに「要 UEFI R3xx」と理由を出すためだけに使う。
  - 前は、知っているデバイスの表から UEFI の版を推定していた。そのため、新しいデバイスに新しい UEFI が要ると書かれていると、実際には新しい UEFI で起動していても入れられなかった。
  - 管理者の側も同じ判断にした。デバイスが無いドライバーは入れない。
- **入れ方を manifest に書く。**
  - `"installAt": "boot"` なら次の起動で入れ替える。`"live"` ならその場で入れる。
  - `Make-Release.ps1` が、GPIO と I2C に `boot`、ほかに `live` を書く。
  - この項目が無い前のリリース（drivers-2026.10.27 まで）は、今までどおり GPIO と I2C を次の起動にする。
- **manifest の確かめ:** ハードウェア ID は `ACPI\` + 英数字の形だけを受け付ける。
- **PC での確認:**
  - 前のリリース（drivers-2026.10.27）でも、GPIO と I2C は次の起動になった。
  - 知らないデバイス（SWOA0901）が manifest の名前「音」で一覧に出た。
  - そのデバイスがあってドライバーが無いときは更新の対象になり、UEFI の推定が R377 でも止められなかった。
  - デバイスが無いときは、対象にならず「要 UEFI」になった。
  - `Make-Release.ps1` の manifest に、名前と `installAt` が入った（候補 2026.10.27.1）。
- **Switch での試験:** 0.5.2 は手で入れない。0.5.1 の「コントロールセンターを 0.5.2 に更新」のボタンで上げる。これが、コントロールセンター自身の更新の初めての試験になる。

## v0.5.1（2026-10-26）: 次の起動での入れ替えと、コントロールセンター自身の更新

### v0.5.0 の「更新する」で起きたこと（I2C、Switch で試験）

- **起きたこと:** pnputil が I2C #1 を 1.0.0.3 に入れ替えたあと、I2C #1 が起動し直さなかった。
  - I2C #1 を使うバッテリー、ファン、CPU のクロックも、止まったままになった。Windows は、DSDT の I2C のつながりを依存関係として扱い、先にそれらを止める。
  - pnputil は返ってこなかった。そのため I2C #5 は 1.0.0.2 のまま残った。
- **記録で分かったこと:** I2C ドライバーの記録は、起動したときの値のままだった（I2C1 の設定前の値が `0x20800`）。新しいドライバーは、I2C #1 でまだ起動していなかった。
- **再起動を試したとき:** 更新の画面が Windows の再起動を止めてしまった。そこで電源を長押しして切り、RCM から起動し直した。
- **起動し直したあと:** 全部「正常」になった。I2C #1 も 1.0.0.3 で動いた。
- **分かったこと:** 新しいドライバーは、起動のときに入っていれば問題なく動く。止まるのは、動いている I2C をその場で入れ替えるときだけ。

### 変えたこと

- **GPIO と I2C は、次の起動で入れ替える。**
  - pnputil では Windows に登録するだけにする（`/add-driver`、`/install` なし）。
  - 古い版のデバイスにだけ「次の起動で入れ直す」印を付ける（ConfigFlags の CONFIGFLAG_REINSTALL）。
  - 印の付いたデバイスは、一覧で「再起動待ち」と表示する。もう一度更新の対象にはしない。
  - 確認の画面と経過の画面でも、次の起動で入れ替わることを知らせる。
- **pnputil を待つのは2分まで。** 過ぎたら「再起動すると入れ替えが終わります」と出す。まだ入れていないドライバーの名前も出す。そのときは、pnputil が使っているかもしれないので、一時フォルダーは消さない。
- **更新の画面が、Windows の再起動やシャットダウンを止めないようにした。** ×で閉じられないのは、ユーザーが閉じようとしたときだけ。
- **コントロールセンター自身の更新（OTA）:**
  - リリースに新しい版があると、「コントロールセンターを x.y.z に更新」のボタンが出る。
  - 押すと、次の順に行う。
    1. 新しい ZIP を `%LOCALAPPDATA%\SwitchWOA\SwitchCenter\update\` にダウンロードする。
    2. SHA-256 を manifest と照らし合わせる。
    3. 展開する。
    4. 展開した新しい版を `--self-update <今のフォルダー> <今のプロセス>` で起動して、今の版は終わる。
    5. 新しい版は、古い版が終わるのを待ってから、自分を今のフォルダーに上書きし、`--open` で起動し直す。
  - 管理者の権限は要らない。今のフォルダーに書き込めないときは、手で入れ替えるように表示する。
  - 前の更新で残ったファイルは、次の起動のときに消す。
- **細かいところ:**
  - 状態の「止まっている」を「停止中」にした。
  - I2C の「動作中」の列に、版を出すようにした（記録の `I2C_0000_DriverVersion`）。
  - 「リリースのページを開く」を、ボタンから離して一番下に置いた。触れたつもりでなくても開いてしまっていたため。
  - リリースのページは、Edge があれば Edge で開く。この Windows の既定のブラウザーは IE11 で、今の GitHub を表示できないため。

### PC での確認

- **比較:** I2C の3つのうち #5 だけが古い場合を確かめた。
  - #5 に印が付く前は、更新の対象になる。
  - 印が付いたあとは、対象にならず、「再起動待ち」が1個と数える。
- **ダウンロード:** 本物のリリース（drivers-2026.10.26）のアプリの ZIP で確かめた。
  - SHA-256 が合い、展開した `SwitchCenter\SwitchCenter.exe` があった。
  - SHA-256 を変えると拒否し、フォルダーを残さなかった。
- **自分自身の入れ替え:** x64 版の2つのフォルダーで試した。
  - 新しい版は、古い版が動いている間は待った。
  - 古い版が終わると、ファイルを上書きして、`--open` で起動し直した。

## v0.5.0（2026-10-26）: ドライバーの更新（OTA）

- **確認:** ドライバーのタブの「更新を確認」で、GitHub の [Windows-for-Switch-Drivers](https://github.com/hayato41200/Windows-for-Switch-Drivers) の最新のリリースの `manifest.json` を読む。

  - 更新できる行は青で表示し、版の後ろに「↑」を付ける。
  - I2C のように同じデバイスが複数あるときは、一番古い版と比べる。
  - デバイスがあるのにドライバーが無いときも、入れる対象にする。デバイスが無いものは対象にしない。
- **UEFI の版:** UEFI は自分の版を Windows に伝えていないので、DSDT にある Switch のデバイスから推定する（例: SWOA0801 があれば R377 以降）。`minUefi` より古ければ「要 UEFI R3xx」と表示し、入れない。

  1. 同じリリースを、GitHub から自分で読み直す。いつもの権限の画面から渡すのは、タグとドライバーの名前だけ。
  2. ZIP を、管理者だけが書ける一時フォルダー（`C:\Windows\Temp\SwitchCenter-OTA-…`）にダウンロードする。
  3. ZIP の SHA-256 が manifest と合うかを確かめる。
  4. 各 .sys の SHA-256 が manifest と合うかを確かめる。
  5. 各 .cat が、このプロジェクトのテスト証明書（`A9E1F054…`）で正しく署名されているかを確かめる。
  6. `pnputil /add-driver <inf> /install` を、GPIO、I2C、バッテリー…の順に行う。
  7. 一時フォルダーを消す。
- **取ってくる場所:** リポジトリは、アプリに固定で書いてある。そのリポジトリのリリースに付いたファイルだけを、HTTPS で取る。
- **終わったとき:** 再起動が必要なら（pnputil の 3010）、そう表示する。
- **新しい版の知らせ:** コントロールセンター自身に新しい版があるときは、リリースのページへのリンクを出す。自分自身の更新は、段階 D で作る。

  - 8つのドライバーすべての .sys と .cat の署名

  - 不正なタグを拒否すること

  - アイコンをダブルクリックしても開く。
  - `SwitchCenter.exe --open` で起動すると、最初から画面を開く。
- **閉じたとき:** ×で閉じても、画面が隠れるだけ。アイコンは残る。アプリを止めるときは、メニューの「終了」を使う。
- **概要:**
  - CPU のクロック、SoC の温度、バッテリー残量、画面の明るさを、大きなタイルで並べる。SoC が 70 ℃ 以上のときは、温度の数字が赤くなる。
  - 詳しい状態として、次を表示する。
    - CPU の電圧、基板の温度、ファンの duty
    - 電源（AC・充電中など）、バッテリーの電圧
    - USB-C の状態
    - 温度による制限
  - 直近5分の SoC の温度（赤）と、CPU のクロック（青）のグラフ。グラフは、画面を閉じている間も2秒ごとに記録している。
- **パフォーマンス:** プロファイルを大きなボタンで選ぶ。選んだものが押された状態になり、今動いているものは太字になる。試験的なプロファイルは黄色で、選ぶと確認の画面が出る。
- **画面:** 明るさのスライダー（3〜100%）。指を離さなくても、動かすとすぐに明るさが変わる。画面の状態（オン、暗くしている、オフ）も表示する。
- **値の取り方:** バッテリーの値は、Windows 標準の API ではなく、ドライバーの記録を使う。標準の API は、この Switch では「バッテリー無し」と返すため。

- **未確認:** Switch での表示。

## SwitchClock との違い

- **動き方:** x86 のエミュレーションではなく、ARM64 のネイティブで動く。
- **配り方:** 1つの exe ではなく、フォルダーで配る。1ファイルにまとめた exe は、起動のたびに中身を展開するので、約3秒かかっていたため。さらに ReadyToRun（事前コンパイル）で、起動を速くしている。
- **設定:** 前回のプロファイルは SwitchClock と同じ場所（`HKCU\Software\SwitchWOA\SwitchClock` の LastProfile）を使うので、そのまま引き継ぐ。
- **自動起動:** 「ログイン時に起動」をオンにすると、SwitchClock の自動起動は消す。2つが同時に起動するのを防ぐため。

メニューの中身（プロファイル、画面の明るさ、ログイン時に起動、終了）と、アイコンの色の意味は、SwitchClock と同じ。

## 手順

1. **SwitchClock を止める。** 動いていたら、メニューの「終了」で閉じる。
2. **コピーする。** `SwitchCenter.zip` を Switch にコピーして展開する。例: `C:\SwitchWOA\SwitchCenter\`。
3. **起動する。** `SwitchCenter.exe` をダブルクリックする。管理者として実行する必要はない。
4. **確かめる。**
   - 通知領域にアイコンが出て、今のクロックが表示されるか。
   - プロファイルと明るさを切り替えられるか。
   - 起動の速さ（アイコンが出るまでの時間）。
5. **（任意）自動起動にする。** 「ログイン時に起動」をオンにして再起動し、SwitchCenter だけが起動するかを見る。
